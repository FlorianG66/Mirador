# Architecture — Mirador

> Vue d'ensemble technique. Le détail et les justifications sont dans `SPEC.md` §5 ; l'avancement dans `PROGRESS.md`.

## Flux de données

```
[Outils tiers] --API / webhooks / MCP--> [Connecteurs] --> [Métriques canoniques]
                                                                      |
[Planificateur 5 min] -------------------------------------> [PostgreSQL] <--> [API FastAPI] <--> [Frontend React]
```

- **Connecteurs** (cœur du produit) : interface `Connector` unique ; un `MockConnector` par catégorie produit exactement le même format qu'un connecteur réel, déterministe via un seed.
- **Métriques canoniques** : clé `module.metric` (ex. `finance.revenue`), unité, période, valeur, dimensions JSONB.
- **Multi-tenant** : chaque table métier porte `organization_id`, chaque requête est filtrée dessus, PostgreSQL RLS en défense en profondeur.

## Structure backend

```
backend/app/
  main.py       create_app(settings) : assemblage (logging, routes, erreurs, engine)
  routers/      HTTP uniquement, aucune logique métier
  connectors/  interface Connector + registre + connecteurs de démo déterministes (4a)
  workers/     planificateur (JobScheduler) + synchro toutes les organisations (4c)
  services/     logique métier
  repositories/ accès aux données
  models/       modèles SQLAlchemy
  schemas/      schémas Pydantic (entrée/sortie)
  core/         config (pydantic-settings), erreurs RFC 9457, logging JSON,
                base asyncpg, tenancy (GUC tenant), deps (session par requête)
```

Couches : `routers → services → repositories`.

- **Multi-tenant** : `users` et `organizations` sont globales (hors RLS) ; `memberships`, `module_permissions`, `invitations`, `audit_logs` portent `organization_id` avec RLS `ENABLE` + `FORCE` et **une seule politique** par table. `app.core.tenancy.set_tenant` pose deux GUC transactionnels (`app.current_user_id`, `app.current_organization_id`) ; `USING` lit l'organisation **ou** l'utilisateur courant, `WITH CHECK` n'accepte que l'organisation courante (empêche l'auto-insertion dans un tenant tiers).
- **Session par requête** : `app.core.deps.get_session` récupère la fabrique sur `app.state.session_factory`, commit en fin de succès, rollback sinon, tenant neutre au démarrage.
- **Repositories** : filtrage explicite **et** RLS (double barrière) ; e-mail des utilisateurs normalisé en minuscules.
- **Sessions** : table `sessions` globale (hors RLS, comme `users`) ; jetons opaques aléatoires, seuls leurs hachages SHA-256 sont stockés ; rotation des deux jetons à chaque rafraîchissement, révocation au logout ; le jeton CSRF appartient à la session (il ne tourne pas).
- **Authentification** : cookies httpOnly + `SameSite=lax` — accès `Path=/` (TTL 15 min), refresh confiné à `Path=/api/v1/auth` (TTL 30 j), CSRF lisible par le JS `Path=/` ; en production les trois sont `Secure`. Mots de passe Argon2id (params OWASP) ; e-mail normalisé ; SIREN facultatif vérifié (9 chiffres + Luhn) ; un message d'erreur unique quels que soient e-mail/mot de passe (aucune énumération, hachage factice pour le minutage).
- **A2F / récupération (2c)** : TOTP RFC 6238 maison (`app/core/totp.py`, secrets 20 octets base32) + 10 codes de secours hachés SHA-256. Connexion avec TOTP actif → cookie `mirador_2fa` (5 min, confiné à `/api/v1/auth`) + défi `auth_challenges` à usage unique ; `POST /auth/2fa/verify` l'échange contre une session. Réactivation régénère secret et codes ; désactivation exige le mot de passe courant. `POST /auth/password/forgot` (réponse invariante, anti-énumération) émet un jeton 30 min haché à usage unique (`password_reset_tokens`) ; `POST /auth/password/reset` change le mot de passe et révoque toutes les sessions. E-mails via `EmailSender` (`LogEmailSender` en dev, SMTP à la phase 11), lien construit sur `Settings.app_base_url`.
- **Invitations, équipe, audit (2d)** : `POST /organizations/{id}/invitations` (admin seul, rate limit `invite` 10/h, TTL 7 j, e-mail via `EmailSender`) crée une ligne `invitations` et journalise `invitation.created` ; le lien porté par l'e-mail contient le jeton **et** l'organisation. `POST /auth/invitations/accept` (compte authentifié dont l'e-mail correspond — 401 absent/expiré, 403 e-mail différent, 409 déjà membre) pose le tenant avant de lire l'invitation, crée le membre, écrit les permissions et journalise `invitation.accepted`. `DELETE …/invitations/{id}` révoque. Équipe : `GET /organizations/{id}/members`, `GET /permissions` (les cinq modules, `none` = absence de ligne, admin = `edit` partout), `PATCH /members/{user_id}/permissions` (audit `membership.permissions.updated` avec avant/après), `DELETE /members/{user_id}` (`membership.revoked`, auto-révocation refusée), `GET /audit-logs`. Les services lèvent `ServiceProblem` (erreurs RFC 9457 via handler global), les routes sans `try/except`.
- **Connexion Google (2e)** : `GET /auth/google` génère un état opaque, le range dans un cookie `mirador_oauth_state` (httpOnly, `SameSite=lax`, 10 min, `Path=/api/v1/auth`) et renvoie l'URL d'autorisation ; `GET /auth/google/callback` compare l'état au paramètre reçu (comparaison à temps constant), échange le code contre une identité via `app.state.oidc_provider` (`GoogleOidcProvider` : jeton puis userinfo en HTTPS, sans vérification locale de JWT), puis session classique — ou défi A2F si le TOTP est actif. Jamais de création de compte : e-mail Google non vérifié → 403, aucun compte à cet e-mail → 403. Fournisseur absent (identifiants absents) → 404 ; échec du fournisseur → 502 avec message figé (détail technique au journal seulement). Identifiants via `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`, URI de retour dérivée de `Settings.app_base_url`.
- **Métriques & connecteurs (4)** : format canonique clé `module.metric` / unité / période / valeur / dimensions (SPEC §5.4), produit à l'identique par les mocks et les futurs connecteurs réels. `app.connectors` (base, `mock`, `registry`) : interface `Connector` (`connect`, `sync(since)`, `handle_webhook`, `disconnect`, `healthcheck`) ; les mocks (finance, web, social, projets) sont déterministes via un seed (32 bits faibles de l'UUID d'org) et réalistes (saisonnalité, tendance, pics). `metric_snapshots` (migration `0005`) : table tenant RLS (comme les autres, une seule politique), unicité `(organization_id, metric_key, captured_at)` → l'upsert rend la re-synchro idempotente ; `unit` ajoutée en `0006` (l'endpoint de lecture est générique et ne connaît pas le connecteur). Worker : `sync_all_organizations` ouvre une session par organisation (tenant posé, commit, panne isolée), déclenché par `JobScheduler` dans le lifespan (`SYNC_INTERVAL_MINUTES`, défaut 5, 0 = éteint). Lecture : `GET /organizations/{id}/metrics/{metric_key}` — garde `view` du module extrait de la clé, course en RLS ; `services.metrics.get_metric_series` (fenêtre `start`/`end`, `limit` ≤ 1000, 404 sans donnée, 422 bornes inversées). `upsert_many` insère par lots de 2 000 lignes (limite de paramètres asyncpg).
- **Identité légale (5e)** : validation SIREN/SIRET (Luhn) et calcul du n° de TVA dans `app/core/siren.py`. `app/services/legal_registry.py` : modèle canonique `LegalCompany`/`LegalLeader`, contrat `LegalRegistry`, client `RechercheEntreprisesRegistry` (API Recherche d'entreprises, `httpx` à transport injectable, cache TTL 24 h, backoff), parsing tolérant, entreprise non diffusible → dirigeants/adresse masqués. Persistance (5e-b) : `legal_profiles` (1:1 organisation, JSONB `dirigeants` et `field_sources`) + `legal_identifiers` (unique `organization_id, pays, schema`, TVA sous `schema="vat"`), migration `0007` RLS. Endpoints `GET`/`PUT`/`POST /organizations/{id}/legal[/refresh]` : provenance par champ (`registry`/`manual` + date), la saisie manuelle prime et l'écart est journalisé (`legal.profile.diverged`), TVA recalculée depuis le SIREN, dirigeants masqués hors admin ; audit `legal.profile.updated`/`refreshed`.
- **Pouls (5f)** : agrégat `GET /organizations/{id}/pulse` (`app/services/pulse.py`, `app/routers/pulse.py`, `app/schemas/pulse.py`). Pas de garde de module : la route restreint **elle-même** chaque KPI aux modules visibles du membre (`PULSE_KPI_KEYS`, 8 clés — `finance.revenue`/`margin`, `web.visitors`/`conversions`, `social.followers`/`engagement_rate`, `projects.open_tasks`/`avg_progress`), chaque KPI portant sa valeur courante et la précédente (tendance côté UI) ; une valeur absente est omise, jamais inventée. Santé **opérationnelle** seulement (`PulseHealthOut` : `good` si tous les modules visibles à KPI ont de la donnée, `warning` sinon, `unknown` si aucun module à métrique n'est visible) — les alertes et objectifs métier arrivent en phase 6. Le fil d'activité (journal d'audit, `services.audit.list_recent`) n'est renvoyé qu'aux administrateurs. Nouvelle lecture `metric_snapshots.get_latest` (du plus récent au plus ancien, l'inverse de `get_series`).
- **Comparaison de périodes (6a-i)** : `GET /organizations/{id}/metrics/{metric_key}/comparison?days=&end=`. Même garde `view` du module extrait de la clé que la lecture de série. `services.metrics.get_metric_comparison` lit **une seule fois** la double fenêtre `[end − 2×days, end]`, répartit les points (`captured_at > end − days` → période courante), agrège chaque fenêtre via `app/services/metric_catalog.METRIC_AGGREGATIONS` (`sum` flux / `last` niveau / `average` taux-durée, repli `sum`) puis renvoie `MetricComparison` (points des deux fenêtres + `change`/`change_percent`, `null` si la période précédente vaut 0 ; 404 sans aucun point, 422 clé/bornes). Un test exige que chaque métrique produite par les quatre connecteurs soit classée dans le catalogue.
- **Objectifs & budgets (6a-iii)** : table tenant `goals` (migration `0008`, RLS) — une ligne par objectif : `metric_key` canonique, `label` libre optionnel, `direction` (`at_least` atteindre au moins la cible / `at_most` rester en dessous, cas du budget), `target_value` et fenêtre glissante `period_days` (1–365). La progression **n'est pas stockée** : `app/services/goals.py` agrège la fenêtre courante via `metric_catalog.reduce_values` (même réduction que la comparaison), la rapporte à la cible (`progress_percent`, `null` si cible nulle) et en déduit un statut — `achieved` (cible atteinte), `off_track` (non atteinte **et** métrique s'éloignant de la fenêtre précédente équivalente), `on_track`, `unknown` (aucune donnée). Endpoints `GET`/`POST`/`PATCH`/`DELETE /organizations/{id}/goals` (`app/routers/goals.py`) : la lecture ne montre que les objectifs des modules visibles (comme le Pouls, jamais de 403) ; créer/modifier/supprimer exige `edit` sur le module préfixe de `metric_key` (vérifié dans le service, seul à connaître la clé après lecture du corps). Audit `goal.created`/`goal.updated`/`goal.deleted`.
- **Tableau de bord personnalisable (6b-ii-a)** : table tenant `dashboard_layouts` (migration `0009`, RLS) — une ligne par couple `(organization_id, user_id)` (contrainte d'unicité), disposition en JSONB (`widgets` = liste de placements `{widget_id, x, y, w, h}`, contrainte `jsonb_typeof = 'array'`). `app/services/dashboard.py` porte le **catalogue** (santé `health`, KPI `kpi.<clé canonique>`, objectifs `goals`, activité `activity`) et la **disposition par défaut** ; le catalogue est filtré par les droits du membre (KPI des modules visibles via la même règle que le Pouls, activité réservée aux admins) et ne compose aucun libellé (le frontend traduit). Endpoints `GET`/`PUT`/`DELETE /organizations/{id}/dashboard` (`app/routers/dashboard.py`) : la mise en page est **personnelle** (aucun droit de module exigé), le `GET` renvoie `available_widgets` + `layout` (enregistrée ou par défaut, `is_default`), le `PUT` remplace la disposition du membre (widget inconnu → 422, non autorisé → 403, doublon ou `x + w > 12` → 422), le `DELETE` restaure le défaut ; à la lecture, un widget devenu interdit est écarté (défense en profondeur). Audit `dashboard.layout.updated`/`reset`. Grille de 12 colonnes, hauteur ≤ 24, ≤ 24 widgets (partagés avec `react-grid-layout` en 6b-ii-b).
- **Sécurité transverse** (`app/core/middleware.py`) : en-têtes de sécurité sur toutes les réponses et CSRF double submit — le cookie `mirador_csrf` doit être repris dans l'en-tête `X-CSRF-Token`, exigé seulement pour les écritures **avec** cookie d'authentification (le 405 d'une route inconnue reste un 405) ; `/auth/register`, `/auth/login` et les routes d'usage anonyme (`/auth/password/*`, `/auth/2fa/verify`) ne l'exigent pas quand il n'y a pas de session jointe.
- **Rate limit** (`app/core/rate_limit.py`) : fenêtre glissante en mémoire par couple (route, IP) sur `app.state.rate_limiter`, 429 + `Retry-After` au-delà du quota ; quotas — `login`, `register`, `verify-2fa` 5/min, `forgot` 3/15 min, `reset` 5/h, `invite` 10/h, `google` 10/min (démarrage + callback partagés) ; un répartiteur ou plusieurs processus devront partager un compteur (v. `DECISIONS.md`).

- **API** : préfixe `/api/v1` ; `/health` (vivacité, sans base) et `/health/db` (200 si PostgreSQL répond, 503 en `application/problem+json` sinon).
- **Erreurs** : handlers globaux (404, 405, 422, 500) au format RFC 9457, titres = phrases HTTP ; jamais d'erreur 500 brute ni de fuite de détail.
- **Logging** : handler unique JSON sur le logger `app` (tous les modules `app.*` y propagent), `propagate=False`, idempotent.
- **Config** : `Settings` (env → `.env`), URL forcée en `postgresql+asyncpg://` ; les settings sont portés par `app.state` et injectés en test via `create_app`.
- **Migrations** : Alembic async (`alembic/env.py` lit les settings), baseline `0001` + `0002` (6 tables phase 2 et RLS) + `0003` (table `sessions`) + `0004` (A2F : colonnes `totp_*` sur `users`, tables `auth_challenges`, `backup_codes`, `password_reset_tokens`, hors RLS) + `0005` (table tenant `metric_snapshots`, RLS) + `0006` (colonne `unit` sur `metric_snapshots`) + `0007` (tables tenant `legal_profiles` et `legal_identifiers`, RLS) + `0008` (table tenant `goals`, RLS) + `0009` (table tenant `dashboard_layouts`, RLS).
- **Tests** : `pgserver` lance PostgreSQL 16.2 éphémère pour les tests (CI incluse, sans Docker), cluster détruit en fin de session (`cleanup_mode="delete"` — sinon ~50 Mo laissés dans le répertoire temporaire par exécution) ; seuil de couverture 80 % ; base vidée avant chaque test (isolation des e-mails uniques).

## Structure frontend

SPA React (Vite) derrière login : pas de SSR (le backend est déjà FastAPI). Client API généré depuis l'OpenAPI (phase 3c). Voir `SPEC.md` §5.2.

```
frontend/

  vite.config.ts        Vite (React + Tailwind v4) + proxy /api → 127.0.0.1:8000 + config Vitest
  eslint.config.js      ESLint flat (JS + TS typé + règles React Hooks + react-refresh)
  tsconfig*.json        TypeScript strict, build par incréments (app + node)
  src/
    main.tsx            montage React, document.title = PROJECT_NAME, import de l'i18n
    App.tsx             routeur (createBrowserRouter) sur la table de routes
    app/routes.tsx      table des routes (AuthProvider > RequireAuth > AppShell + gardes par module)
    api/                client typé : schema.d.ts (généré), client.ts (CSRF/ApiError), types.ts
    auth/               context.ts (useAuth), AuthProvider.tsx, guards.tsx (RequireAuth/Module/Admin)
    components/
      layout/           AppShell (menu latéral + topbar), Sidebar, SidebarNavItem,

    metrics/            panneaux de module : queries.ts (clés/helpers communs),
                        finance.ts (8 clés), web.ts (10 clés), social.ts (9 clés) et
                        projects.ts (10 clés), format.ts (Intl)
    legal/              fiche légale : queries.ts (lecture/PUT/refresh), mentions.ts
                        (champs, dates, assemblage des mentions), ProvenanceBadge.tsx,
                        LegalEditForm.tsx
    pulse/              vue d'ensemble (5f) : queries.ts (agrégat /pulse, polling 5 min),
                        format.ts (métadonnées des KPI, tendance, horodatage relatif,

    search/             recherche globale (6b-i) : items.ts (index statique des pages et
                        KPI clés, normalisation casse/accents, filtré par permissions),
                        SearchPalette.tsx (dialogue Ctrl/Cmd+K, flèches + Entrée)
    pages/              DashboardPage, FinancePage, WebPage, SocialPage, ProjectsPage,
```

- **Design system (3b)** : couleurs et rayons en variables CSS (`:root` clair, `.dark` sombre) exposées à Tailwind par `@theme inline` ; les composants n'utilisent que des tokens sémantiques (`bg-surface`, `text-muted`, `text-danger`…). Thème piloté par la classe `.dark` sur `<html>` (hook `useTheme`, préférence dans `localStorage` ; `prefers-color-scheme` seulement à la première visite), amorcé par un script inline pour éviter le flash.
- **Layout** : `AppShell` = rail rétractable gauche (`useRailCollapsed`, largeur `--rail-w`) + topbar + contenu ; sur mobile le menu coulisse (overlay, fermeture par Échap). Lien d'évitement vers le contenu et `aria-current` actif sur la navigation (WCAG AA). `PageHeader` = en-tête de page partagé (titre + description).
- **i18n** : aucun texte en dur (AGENTS.md §7) ; ressources FR/EN embarquées, `initAsync:false` (init synchrone), `<html lang>` suit la langue active.
- **Animations** : transitions de page via Motion (fondu + glissement), compteurs animés via `requestAnimationFrame` ; toutes neutralisées si `prefers-reduced-motion: reduce`.
- **Routing** : React Router ; chaque module est gardé par `RequireModule` (`view`/`edit`) ; les cinq modules de la phase 5 (`/finance`, `/web`, `/social`, `/projects`, `/legal`) ont une vraie page, sans données en dur (AGENTS.md §8).
- **Panneaux de module (5a/5b/5c/5d)** : `src/metrics/*` charge les clés canoniques d'un module en `Promise.all` (polling 5 min) — un 404 signifie « module pas encore connecté » (`isNotFound`), toute autre erreur affiche l'état d'erreur avec réessai. `FinancePage` (`/finance`, 8 clés), `WebPage` (`/web`, 10 clés pilotées par les sessions), `SocialPage` (`/social`, 9 clés pilotées par les abonnés cumulés) et `ProjectsPage` (`/projects`, 10 clés pilotées par le stock de tâches ouvertes) partagent `MultiSeriesChart` (Recharts, couleurs par tokens) et `RankedList` (répartitions construites sur `dimensions.items`) ; les valeurs sont formatées par `format.ts` (`Intl`, dont `formatCountry` via `Intl.DisplayNames` et `formatDays` en unité `day`), jamais à la main.
- **Fiche légale (5e-c)** : `src/legal/*` — `LegalPage` (`/legal`, gardée par `RequireModule moduleKey="legal"`) charge la fiche via `useLegalProfile` puis `PUT`/`POST refresh` par mutation (mise à jour optimiste du cache TanStack Query, pas de polling). Provenance par champ affichée par `ProvenanceBadge` (registre/manuel + date), dirigeants visibles des seuls admins, bloc « mentions légales » assemblé par `mentions.ts` et copié via `navigator.clipboard`, export PDF par `window.print()`. `LegalEditForm` n'envoie que les champs modifiés pour préserver la provenance des champs inchangés.
- **Vue d'ensemble « Pouls » (5f)** : `DashboardPage` (route d'accueil `/`) charge l'agrégat via `usePulse` (`src/pulse/queries.ts`, polling 5 min) et rend les widgets de la disposition servie par l'API (v. 6b-ii-b) : cartes `KpiCard` des KPI clés autorisés, badge de santé (rôle `status`), fil d'activité et panneau d'objectifs (`GoalsPanel`, v. 6a-iv). `src/pulse/format.ts` porte les métadonnées des KPI (`KPI_META` → clés i18n `finance.*`/`web.*`/`social.*`/`projects.*` **réutilisées**), la tendance (`kpiTrend`) et l'horodatage relatif (`Intl.RelativeTimeFormat`) ; les libellés restent dans l'i18n (`dashboard.*`), aucune donnée en dur (AGENTS.md §8).
- **Comparaison de périodes (6a-ii)** : un sélecteur 7 j / 30 j / 90 j (`PeriodSelect`, défaut 30 j) sur le tableau de bord lance, via `useQueries`, un `GET /metrics/{clé}/comparison?days=` par KPI clé du Pouls (les clés viennent du Pouls, donc déjà filtrées par droits). Chaque `KpiCard` affiche alors `summary.current_value` et `summary.change_percent` ; si la comparaison renvoie 404 (aucune donnée sur la fenêtre), échoue ou charge encore, la carte retombe sur `kpi.value`/`kpiTrend` du Pouls — aucun KPI isolé ne passe en erreur. `PeriodSelect` et les constantes `PERIOD_OPTIONS`/`DEFAULT_PERIOD_DAYS` sont partagés (`src/components/ui/`, `src/metrics/queries.ts`).
- **Objectifs & budgets (6a-iv)** : `src/goals/*` — `GoalsPanel` (carte du tableau de bord, à côté du fil d'activité) liste les objectifs visibles avec leur progression et leur statut (`GoalStatus` recalculé par le backend, jamais stocké côté client) et permet créer/éditer/supprimer quand l'utilisateur a le droit d'écriture sur le module de l'indicateur (`canEditMetric` : admin = tout, sinon `edit` requis ; un membre en `view` ne voit aucune action). `GoalForm` (création **et** édition) réutilise `PeriodSelect` pour la fenêtre et restreint l'indicateur aux KPI clés du Pouls (`KPI_META`, libellés réutilisés) ; toute écriture (`useCreateGoal`/`useUpdateGoal`/`useDeleteGoal`) invalide la liste. Statut « en dérive » (`off_track`) mis en évidence (badge + barre rouges) ; libellés i18n `goals.*` (FR/EN).
- **Recherche globale (6b-i)** : `src/search/*` — l'index (`items.ts`) est dérivé du **catalogue statique** de l'application : les pages (vue d'ensemble, modules visibles via `canSeeModule`, Équipe réservée aux admins, paramètres) et les 8 KPI clés du Pouls (`KPI_META`, libellés i18n réutilisés). `normalizeText` (NFD + suppression des diacritiques) et `searchItems` (sous-chaîne sur le libellé **et** la ligne secondaire — le module porteur d'un KPI, bornée à 8). `SearchPalette` est un dialogue contrôlé par l'`AppShell` (props `open`/`onOpen`/`onClose`/`permissions`), ouvert par un écouteur global **Ctrl/Cmd+K** ou par le bouton « Rechercher » de la topbar, fermé par Échap ; navigation flèches + Entrée ou clic (motif combobox : `role="combobox"`/`listbox`/`option`, `aria-activedescendant`, `aria-selected`), focus déplacé sur le champ à l'ouverture et rendu à l'élément précédent à la fermeture. Aucun appel API : l'index est filtré par les permissions de la session (décision notée dans `DECISIONS.md`).
- **Tableau de bord personnalisable (6b-ii-b)** : `src/dashboard/*` rend la disposition servie par l'API (6b-ii-a) sous forme de widgets déplaçables et redimensionnables. `layout.ts` (fonctions pures : `toGridLayout`/`toPlacements`/`sameLayout`/`widgetTitleKey`, constantes `GRID_COLUMNS`/`ROW_HEIGHT`/`GRID_MARGIN`) fait le pont avec `react-grid-layout` (items `i`, mêmes unités de grille que le serveur) ; `widgets.tsx` porte le rendu par genre (`health`/`kpi`/`goals`/`activity`) et le type `WidgetData` assemblé une fois par la page ; `DashboardGrid.tsx` enveloppe la grille (largeur mesurée localement, repli sûr sans `ResizeObserver`) ; `queries.ts` expose `useDashboard`/`useSaveDashboard`/`useResetDashboard` (GET/PUT/DELETE `/dashboard`, écriture par mutation, remise à zéro par invalidation). En lecture la grille est immobile ; le bouton « Personnaliser » ouvre le mode édition (poignée de déplacement `.widget-handle`, redimensionnement par le coin bas-droit, boutons Enregistrer/Annuler/Réinitialiser). Un widget enregistré puis devenu interdit est écarté (le backend filtre déjà à la lecture) ; le fil d'activité n'est jamais servi à un membre (le backend l'écarte du catalogue — aucune garde côté client, décision notée dans `DECISIONS.md`). Libellés i18n `dashboard.*` (FR/EN).
- **Export PDF (6c-i)** : `components/ui/PageHeader.tsx` reçoit l'option `printable` qui ajoute un bouton `PrintButton` (« Exporter en PDF », appelle `window.print()`) et un bandeau `PrintHeader` (nom du produit, date de génération, période rappelée) rendu uniquement à l'impression. La feuille `src/index.css` ajoute une section `@media print` : elle **force le thème clair** (un `.dark` imprimé serait illisible sur papier), masque l'interface (rail, barre supérieure, actions — utilitaire `print:hidden`) au profit du contenu et fixe les marges de page (`@page`). L'export est proposé sur la vue d'ensemble (en rappelant la période) et sur les pages Finance/Web/Réseaux sociaux/Projets/Identité légale ; le bouton ad hoc de la fiche légale est remplacé par ce composant partagé. Technique retenue (impression du navigateur, aucune dépendance serveur) et alternative écartée : `DECISIONS.md`. Libellés i18n `print.*` (FR/EN).

- **Client API (3c)** : `backend/scripts/export_openapi.py` exporte le schéma (`create_app().openapi()`) vers `frontend/openapi/schema.json` (commité) ; `openapi-typescript` en génère `src/api/schema.d.ts` (script npm `generate:api`, exclu d'ESLint) ; les appels passent par `openapi-fetch` (`src/api/client.ts`, `baseUrl` = origine courante, cookies inclus). Un middleware ajoute `x-csrf-token` (copie du cookie `mirador_csrf`) sur les méthodes non sûres ; un échec HTTP devient `ApiError` (RFC 9457) ; `unwrap` renvoie les données ou lève.
- **2FA (3d-b)** : route publique `/2fa` (défi après `totp_required` au login, `POST /auth/2fa/verify`) ; route protégée `/settings` (activation `POST /auth/2fa/enable`, désactivation `POST /auth/2fa/disable`) ; lien Paramètres dans la sidebar.
- **TanStack Query (3d-a)** : `@tanstack/react-query@5.104.1` — `QueryClientProvider` dans `main.tsx` (retry false, refetchOnWindowFocus false). `AuthProvider` utilise `useQuery` pour `/auth/me` (clé `authKeys.me`) et les permissions (clé `authKeys.permissions` orgId) ; `reload()` = `invalidateQueries({ queryKey: authKeys.me })`. Les formulaires (login, inscription, forgot/reset password) utilisent `useMutation` de TanStack Query avec `unwrap` du client API.
- **Auth & gardes (3c)** : `AuthProvider` charge `/auth/me` puis les permissions de l'organisation active (mémorisée dans `localStorage`, sinon la première) ; états `loading`/`anonymous`/`authenticated`/`error`. `RequireAuth` redirige vers `/login` si non connecté ; `RequireModule` et `RequireAdmin` rendent `ForbiddenPage` (403) faute de droits ; le menu latéral filtre les modules visibles (un admin voit tout, `Équipe` lui est réservée).Qualité frontend : `npm run lint` (ESLint, aussi en hook pre-commit), `npm run typecheck` (`tsc -b`), `npm test` (Vitest, environnement jsdom), `npm run build` (`tsc -b && vite build` ; bundle non gzippé > 500 kB à ce stade, v. `DECISIONS.md`). En dev, le backend doit tourner sur `127.0.0.1:8000` (uvicorn) et le navigateur ouvre `http://localhost:5173`.
