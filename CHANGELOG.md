## [Non publié]

### Ajouté
- Socle frontend (phase 3, sous-phase 3a) : Vite 8 + React 19 + TypeScript strict (5.9.3) + ESLint flat (config uniquement) + Vitest 5 (jsdom, jest-dom) ; proxy de dev `/api` vers le backend FastAPI (same-origin, pas de CORS en dev) ; `PROJECT_NAME` centralisé dans `src/constants.ts` (AGENTS.md §1) ; versions épinglées sans caret — TypeScript 5.9.3 car `typescript-eslint` 8.71.1 exige `< 6.1` (TS 7 « latest » pas encore compatible).
- Connexion Google (phase 2, sous-phase 2e) : `GET /auth/google` (état en cookie httpOnly 10 min) et `GET /auth/google/callback` (comparaison à temps constant, échange du code via `GoogleOidcProvider` — jeton puis userinfo en HTTPS, sans vérification JWT locale), session classique ou défi A2F conservé si le TOTP est actif ; compte existant uniquement (e-mail non vérifié → 403, compte absent → 403), fournisseur non configuré → 404, échec du fournisseur → 502 à détail figé ; rate limit `google` 10/min partagé démarrage/callback, variables `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` dans `.env.example`, `httpx` promu dépendance runtime.
- Invitations, permissions et audit (phase 2, sous-phase 2d) : création d'invitation par un admin (TTL 7 j, rate limit 10/h, lien d'acceptation portant l'organisation, e-mail via `EmailSender`), acceptation par un compte authentifié dont l'e-mail correspond, révocation d'invitation ; équipe (liste des membres, permissions par module sur les cinq modules, `none` non stocké — l'absence de ligne vaut `none`, admin = `edit` partout), révocation d'un membre (auto-révocation refusée) ; journal d'audit des actions sensibles (`invitation.created/revoked/accepted`, `membership.permissions.updated`, `membership.revoked`) consultable via `GET /audit-logs`.
- A2F TOTP et récupération de compte (phase 2, sous-phase 2c) : TOTP RFC 6238 implémenté en interne (vecteurs officiels vérifiés), activation/désactivation à deux facteurs avec 10 codes de secours hachés (SHA-256), défi de connexion à usage unique (cookie `mirador_2fa` 5 min), mot de passe oublié (jeton 30 min haché, usage unique, révocation de toutes les sessions au reset), interface d'e-mails (élémentaire en dev, SMTP à la phase 11), rate limits dédiés, migration Alembic `0004`.
- Authentification phase 2, sous-phase 2b : inscription (compte + organisation + admin), connexion e-mail/mot de passe (Argon2id, anti-énumération), rotation et révocation des sessions, `/auth/me`, cookies httpOnly (accès 15 min / refresh 30 j), CSRF double submit sur couche middleware, rate limit d'authentification en mémoire, vérification du SIREN (Luhn), migration Alembic `0003` (table `sessions`).
- Modèle de données phase 2, sous-phase 2a : tables `organizations`, `users` (globales) et `memberships`, `module_permissions`, `invitations`, `audit_logs` (tenants, RLS activée et forcée, une politique par table), migration Alembic `0002`, gestion du tenant par GUC transactionnels, session par requête (`get_session`) et repositories `organizations` / `users` / `memberships`.
- Backend socle FastAPI (phase 1) : `create_app` avec préfixe `/api/v1`, endpoints `/health` et `/health/db`, erreurs RFC 9457 (`application/problem+json`), logging JSON structuré, configuration pydantic-settings, accès base asyncpg, migrations Alembic (baseline `0001`) et suite pytest sur PostgreSQL réel via pgserver.
- Fondations du repo : structure monorepo, Docker Compose (PostgreSQL), pre-commit, CI avec gitleaks + job backend (ruff, mypy, pytest).
